# Finance

> **Status:** Active
> **Last reviewed:** 2026-11-10

## Overview
Personal financial planning: users build *plans* (scenarios) with incomes,
expenses, and debts, then confirm monthly actuals so projections stay
calibrated. Health scoring and scenario comparison are part of this module,
and so is the trading journal (`/portal/trading`), whose balance the plans
count and project at its own recent pace.

## Routes
- `/portal/plans` — list of plans
- `/portal/plans/new` — create plan
- `/portal/plans/[id]` — plan detail + editor; `?view=table` / `?view=calendar` opens that Overview view (the switcher keeps it in the address via `history.replaceState`, so a reload stays put — `lib/finance/plan-view.ts`)
- `/portal/plans/compare` — side-by-side scenario comparison
- `/api/plans/assistant` — the plans assistant's chat, `POST`, streamed as NDJSON (`PlansAssistantEvent` per line); admins with `ANTHROPIC_API_KEY` only (`canUseAssistant`)
- `/portal/trading` — the trading journal, laid out like a plan: one screen-tall panel (from `xl`) with the balance as its headline and a Calendar / Analytics / Trades switcher, and a column beside it for that view. Calendar: each day's P&L, a trade held several days as a bar across them, a Week column; beside it the month's figures and the picked day. Analytics: the equity curve and P&L by month and weekday; beside it the stats and P&L by symbol or setup. Trades: the list; beside it deposits and withdrawals. `?view=analytics` / `?view=trades` opens that view (`lib/finance/journal-view.ts`). An empty journal shows all of it at zero
- `/api/trading/assistant` — the trading assistant's chat, `POST`, streamed as NDJSON (`TradingAssistantEvent` per line); admins with `ANTHROPIC_API_KEY` only

## Server actions — `/app/actions/`
- `finance-plans.ts` — CRUD + lifecycle for finance plans (create, update, delete, clone, set-as-main, `setPlanColorAction`) and projection calculations. `createPlanAction` stamps `balances_as_of` with the reader's today; `updatePlanAction`, `addPlanDebtAction` and `updatePlanDebtAction` ask `restateOpeningBalances` for a restatement when the edit changes an opening balance (see *Opening balances are dated*); `updatePlanAction` takes as edits only the balances the payload carries. Every action returns `ActionResult<X>`; every mutation calls `revalidatePlans()` (the `/portal/plans` layout **and** `/portal`, whose dashboard card shows the main plan)
- `finance-plans.ts`: every plan / line mutation is a thin `planAction` around its operation in `finance-plan-operations.ts` (auth gate, reader's calendar, `PlanOperationError` → the action's error, revalidation)
- `plans-assistant.ts` — `applyPlanChangesAction`: re-checks a proposal the user approved and writes it through the plan operations (`applyPlanChanges`)
- `finance-confirmations.ts` — save monthly confirmation snapshots and per-debt balance confirmations
- `dev-tools.ts` — `runDailySnapshotsAction` (admin-only): runs the daily finance + portfolio snapshot job on demand, surfaced via the dev drawer
- `trading-journal.ts` — create / update / close / delete a trade, add / delete a deposit or withdrawal; each revalidates `/portal/trading`, the plans layout and `/portal` (a plan counts the account)
- `trading-assistant.ts` — `applyTradingChangesAction`: re-checks a proposal against the journal as it is now and writes it in one transaction

## Services — `/lib/services/`
- `finance-plan-service.ts` — `listUserPlansWithLines` (every plan with its lines in five queries, for the list and compare pages); `updateIncome` / `updateExpense` / `updateDebt` / `updatePlan` throw a not-found error when no row on the caller's plan matched; `clonePlan` runs in one transaction and copies the per-month overrides re-pointed at the new lines (`cloneOverrides`; confirmations are not copied) and `balancesAsOf`. `createPlan(userId, data, today)` sets `balancesAsOf`; `updatePlan` / `addDebt` / `updateDebt` take an optional `PlanRestatement` and then write the whole restated set (plan balances, every debt's opening balance, `balancesAsOf`, and a same-day confirmation) in one transaction. `projectionOptionsFor(plan, userId, prefetched?)` is the ONE place projection options are assembled (portfolio value + weighted growth when included — the portfolio includes the market value of assets the user runs for other people (`getManagedAssets`), passed as `portfolioHeldValue` and grown at `portfolioHeldMonthlyGrowthRate` — the owner's EXPECTED return, each method's `expected_monthly_roi` weighted by its holdings (`expectedManagedRate` in the margin service; a method with none holds flat). The user's own holdings grow at their methods' promised `monthly_roi`, so a client's plan (the owner's sister) compounds at what she was promised; auto-invest ROI, overrides, `asOf`); `projectPlanWithPortfolio` uses it. `getAutoInvestRates` (many methods' ROIs in one query) feeds its `prefetched.autoInvestRate`. `upsertLineOverride` refuses a line that isn't on the plan (checked in its transaction). Re-exports the engine (`projectPlan`, `projectStateAt`, `compareDebtStrategies`, `deriveFinanceMood`) from `lib/finance/projection.ts`, and `setPlanColor` (colour-only update for the rail swatch)
- `finance-confirmation-service.ts` — confirmations, `getLatestConfirmations` (every plan's latest in two queries) + `autoConfirmSkippedPeriods` (cron baseline roll-forward). A confirmation is matched to the period that CONTAINS its day, never by exact key (see *Calculation semantics*)
- `finance-snapshot-service.ts` — `calibratePlan` (pure) / `buildCalibratedPlan`, `loadCalibratedView` (calibrate + project + today in one call), `loadPlanOverviews` (list/compare: every plan calibrated, projected and put on a timeline, with confirmations, auto-invest rates and history batched), snapshots, `restateOpeningBalances` (the restated opening set for an edit, or null when nothing changed), `getProjectedStateOnDay` (confirmation pre-fill), and `getFinanceMood` (request-cached; the main plan's calibrated outcome as a mascot pose)
- `finance-plan-operations.ts` — one function per plan change (`createPlanOperation`, `copyPlanOperation` (a clone or scenario, returning where each line went; it keeps the source's opening balances and its debts' `debt_key`, so the user's confirmations calibrate both alike and they open on the same day at the same figures. The Clone and Scenario actions run it too), `updatePlanOperation`, `deletePlanOperation`, `setMainPlanOperation`, `add/update/delete{Income,Expense,Debt}Operation`, `recordPlanMovement`): validate, restate the opening balances the change moves, write, log under impersonation, record the movement snapshot. The actions and the plans assistant both run them; `PlanOperationError` is an expected refusal
- `plans-assistant-service.ts` — the plans assistant's reads (`listAssistantPlans`, `getAssistantPlan`, `compareAssistantStrategies`, each with a `PlanOutlook`), `previewPlanChanges` (plays a proposal on a copy of the plans: patches merged over stored rows, checked by the form schemas, balances restated as a save would, outlook before/after) and `applyPlanChanges` (plays it again, then runs each change through its operation in order; `PlanChangeError` says where it stopped)
- `interest-service.ts` — interest/ROI math (shared with [Portfolio](./portfolio.md))
- `trading-journal-service.ts` — `getTradingJournal(userId, timeZone)` (request-cached; every day read on the reader's calendar), `getTradingSummary` (balance, its day and the monthly pace a plan grows it at; null with no journal) and the writes. A withdrawal cannot take the balance below $0.00, and neither can deleting a deposit the account already paid out. Both, and the assistant's change sets, run under `withJournalLock` — one transaction-scoped advisory lock per user — so two cash-outs sent at once are checked one after the other
- `trading-assistant-service.ts` — `getAssistantJournal` (what the model reads), `planTradingChanges` (pure: checks a change set on an in-memory copy, so a deposit can fund a later withdrawal, and works out the card's lines, the account before / after and the writes), `previewTradingChanges`, `applyTradingChanges` (one transaction, under the journal's lock)

## Pure finance maths — `/lib/finance/`
- `projection.ts` — the engine: `projectPlan`, `projectStateAt` (THE "today" figure), `compareDebtStrategies`, `deriveFinanceMood`. Client-safe, so the editor and the server run the same maths
- `schedule.ts` — `planOccurrences`: every dated occurrence of a plan's lines with overrides applied (skip / amount / reschedule, including moves into another month or period). The engine, the today figure, the sidebar breakdowns and the calendar all read it. `RESCHEDULE_MARGIN_MONTHS` / `rescheduleWithinReach` bound how far one occurrence may move; `monthYearOfKey` turns an occurrence's cadence month into its override key
- `receivables.ts` — `owedRepayments` (every repayment of an income marked `owedToMe`, walked to its own end date, past the horizon if need be) and `owedAfter` (what is still owed once a day is over). The engine adds it to net worth as `receivables` on every period close and on the today figure
- `opening-balances.ts` — `changesOpeningBalances` (cheap check: may an edit change an opening balance), `effectiveEdits` (the edits that do, judged against today's position) and `restateOpeningSet` (the set restated as of today)
- `period.ts` — accounting-period helpers (unchanged)
- `plan-colors.ts` — `PLAN_COLORS` (the palette's five slots, in order) and `nextPlanColor`: a new plan, a copy (Clone, Scenario, the assistant's `create_plan` / `copy_plan`) and the new-plan form's default all take the first slot none of the user's plans wears (the least worn once all five are), so two plans never share a line colour by accident. `createFinancePlanSchema.color` is optional for this
- `line-groups.ts` — the Setup list's grouping: lines sharing a name become one row (the amount that applies today, "N phases" and their span), and on the income side every `owedToMe` line goes into one collapsed "Owed to you" section with the total still owed (`owedRepayments`/`owedAfter`, the net-worth rule)
- `chart-series.ts` — `buildPlanTimeline` / `buildChartSeries` (real past as period closes + projection), `alignTodayPoint`, `buildCompareRows` (compare chart, joined by calendar month), `calendarTicks` (axis ticks on calendar months), `forecastKpiPoints` (the "Next" KPI; a plan that has not started yet gets its first close, no today marker and no Confirm), `milestoneCrossings`, and the one debt-free definition (`debtFreeMonthsFromNow`, `describeDebtFree`, `formatDebtFree`, `summaryDebtFree`)
- `scenario.ts` — `compareScenario` (scenario vs base at a shared period; payoff compared as dates)
- `dashboard.ts` — `buildDashboardFigures` for the dashboard card: the last three closed periods (`DASHBOARD_PAST_MONTHS`), today and the next 12 closes as net worth's parts (savings, investments with the portfolio folded in — own money plus the managed margin, trading — owed to you, debt; `positions` for the managed note), each point named after the month its period CLOSES in (`anchorDay`); `pastCount` says where today sits. `dashboardGoal` (`DashboardGoal`) — the debt-free date while there is debt (small print under Debt, the margin note's type), then the next net-worth milestone the projection reaches (under net worth)
- `debt-payments.ts` — `projectedDebtPayments` / `debtChipAmount`: the calendar's debt chips read the payments the projection made
- `table-rows.ts` — `densify` (first 12 rows + real Decembers)
- `amount-input.ts` — parses typed or pasted amounts ("$1,234.50") the way the server schema will, so the confirmation dialog shows per-field errors instead of a bare "Invalid input" toast
- `recurrence-label.ts` — `describeRecurrence`: the Setup tab's schedule column ("Every 6 months on the 12th"), never "Day 12 · monthly" for a six-monthly line
- `milestones.ts` — default milestone list
- Shared, outside the module: `lib/utils/date.ts` (`todayInTimeZone`, `calendarDayInTimeZone`, `earliestCalendarDay`, `TIME_ZONE_COOKIE`), `lib/utils/request-today.ts` (server: `getRequestToday` / `getRequestTimeZone` from the `tz` cookie), `hooks/use-time-zone-cookie.ts` (written by `AppHeader`), `lib/utils/format.ts` (`roundCents`, `moneySign`, `CENTS_EPSILON`), `lib/utils/chart-axis.ts` (`niceTicks` / `yAxisWidth`: the Y ticks recharts would draw, passed in so the plan and dashboard charts size their axis to the labels)
- `trading.ts` — `tradePnl` (direction × move × quantity × multiplier − fees), `buildJournal` (balance = deposits − withdrawals + closed trades' P&L; stats, days, equity curve, breakdowns), `journalMonths` (a month's return = its P&L ÷ the opening balance plus that month's deposits; a day's deposit and withdrawal each count in full, never as their difference) and `trailingMonthlyRate` (the average return of the last six complete months, the current one excluded — a plan's pace; each month counts for at most ±100%, `MAX_MONTHLY_RETURN`, so one month on a near-empty account cannot set the pace)

## DB tables — `db/schema.ts`
- `finance_plans` — user's financial scenarios. `balances_as_of` (date, nullable; migration `0052_faithful_hiroim`) is the calendar day the opening balances were last set on; the same migration dropped `finance_plans_initial_savings_chk` so a restated overdraft can be stored. `auto_invest_custom_rate` (numeric 9,6, nullable, `>= 0`; migration `0059_parallel_timeslip`) is a monthly return the user sets for the auto-invest bucket: set, it wins over `auto_invest_method_id`'s ROI (`getAutoInvestRate`, and `loadPlanOverviews` for the list); the Settings form offers *Portfolio method* or *Custom return* (typed as %/mo, stored as a decimal)
- `finance_plan_incomes` — income line items. `owed_to_me` (boolean, default false; migration `0054_superb_smasher`) marks someone paying back money they owe the user
- `finance_plan_expenses` — expense line items
- `finance_plan_debts` — tracked debts within a plan. `debt_key` (uuid, nullable; migration `0061_lucky_lady_mastermind`) is the debt across plans: a copy keeps its source's key, null means the line's own id (`debtKeyOf`). Confirmed balances are matched to it, so one confirmation recalibrates every plan's copy of the debt
- `finance_plan_snapshots` — the USER's history. `portfolio_value` (numeric, nullable; migration `0062_moaning_blazing_skull`) is the portfolio inside `net_worth`, so the chart's past can draw it; `mapPortfolioValues` draws $0 for older rows, from where the other series start (migration `0061`: `user_id`, `plan_id` nullable and `SET NULL` on delete — it only records which plan was main). Only the main plan writes it; every plan reads it as its past; rows without `user_id` (written by older code) count only as the current main plan's (`snapshotsOf` in [`finance-history.ts`](../../lib/services/finance-history.ts)). The migration deleted what non-main plans had recorded. `source = 'movement'` (enum value added in migration `0060_complex_skullbuster`) is a DAY's position (`projectStateAt`, the dashboard's Today), not a period opening: every period-history reader (`getRecentMonthlySnapshots`, `recentSnapshotsForPlans`) excludes it
- `finance_plan_snapshot_debts` — per-debt balance breakdown for each snapshot; `debt_key` names the debt, `debt_id` goes null when its line is deleted
- `finance_plan_confirmations` — user-confirmed monthly actuals (`source`: `user` | `auto`). The USER's, like the snapshots (`user_id`, unique per `(user_id, confirmation_month)`); confirmed and auto-confirmed on the main plan only, and the latest one calibrates every plan (`getLatestConfirmation(userId)`)
- `finance_plan_debt_confirmations` — per-debt balance confirmations, by `debt_key` (`debt_id` goes null with its line)
- `trading_trades` (migration 0064) — one trade: symbol, side, quantity, multiplier (contract size), entry / exit price, opened / closed at, fees, setup, notes. Exit price and close time are both null (open) or both set
- `trading_cash_movements` (0064) — deposits and withdrawals of the trading account

## Notes
- **The plans assistant proposes; the user applies** (2026-11-03). Same gate, model and loop as Travel's and Sports' (`lib/ai/assistant/`), spend booked as `plans-assistant`, no web search. Its tools live in `lib/plans/assistant/converse.ts` on the shared toolbox: `list_plans`, `get_plan`, `compare_strategies`, `open_plan`, `propose_plan_changes`. A proposal is played in memory with the app's own projection (nothing written) and drawn as a card; Apply re-validates it from scratch and writes through `finance-plan-operations` — the forms' exact path, restatements, impersonation log and movement snapshots included. The proposal is checked whole before any write; the operations are not one transaction, so a write that still fails part-way keeps the changes before it and says so. No undo yet (Travel has one). A copy keeps its source's line ids in memory, so the preview needs no mapping; Apply clones through `clonePlanWithLineIds` and maps each named line onto the copy's. A loan the user makes is two lines — a one-time expense the day it leaves, and an `owedToMe` income for each repayment — which the prompt spells out.
- Conventional Commits scope: `finance`
- **Today's figure routes the surplus as soon as the cash lands** (`routeLandedCash`, 2026-11-03). ## Calculation semantics (audit 2026-09-29)

Regression tests live next to the code (`lib/finance/*.test.ts`, `lib/services/finance-*.test.ts`, `schemas/finance.test.ts`, `lib/utils/{date,format}.test.ts`, `components/finance/plan-calendar.test.tsx`, `app/actions/finance-plans.test.ts`); the numbers in them are the audit's worked examples.

- **As-of day.** Opening balances are read on a day: a user confirmation's day, the plan's `balances_as_of`, or — on rows from before that column — the creation day (a scenario inherits its base plan's). Inside the period that contains it, occurrences dated on/before it are already in the balances — they still count in the period's income / expense / debt-payment totals (the period's budget) but are not applied again (`ProjectionMonth.preAsOfCashFlow`), and every rate in that period (debt interest, savings and investment interest, portfolio growth) accrues only for the days that remain. An as-of day outside the first period is ignored (calibration rebases a later one so it lands in period 0). Confirming late in a period no longer double-counts that period's paycheque and bills; the confirmation dialog pre-fills the projected position ON today, so saving it unchanged moves nothing.
- **Occurrences.** Every surface resolves line dates through `planOccurrences`: day-31 lines clamp to month-end; weekday rules fall back to the last weekday; a period that holds two hit dates counts both (income AND debt payments — debts used to pay only the first); a rescheduled occurrence moves in the projection too, even into another period.
- **Debts.** Interest accrues day-weighted between payment dates (one monthly rate per period). The final payment is capped at the balance; percent-of-balance minimums are recomputed on the balance. The calendar's debt chips show the payment the projection made (nothing once paid off).
- **Surplus routing.** Avalanche / snowball roll over the FULL minimum of every debt already paid off, then add `surplusToDebtsPercent` of what is left, as extra principal in strategy order; "none" rolls nothing. Extra payments and auto-invest never exceed the cash on hand — nothing is borrowed to prepay or invest while savings are overdrawn. Savings and investments earn their rate on the period's OPENING balance.
- **Strategy picker.** Every row runs with the plan's own surplus share (no forced 60%); at 0% the picker says the strategies only decide where freed minimums roll over. The comparison uses the same options as the chart (portfolio growth included).
- **Debt-free.** One definition everywhere: months from today until the payoff period (`debtFreeMonthsFromNow`), shown with its month ("Debt-free in 4 mo · Dec 2026"). Debts that all start at $0 read "No debt".
- **Scenario vs base.** Clones copy overrides (re-pointed), not confirmations. The ghost line and the delta card compare both plans as written, from the base plan's as-of day, at the SAME period (the earlier end date), with payoff compared as dates.
- **Compare chart.** Rows are calendar months; each plan contributes its own point for that month (plans were joined by array index). The rail's NW shows the date it describes.
- **Table.** "Debt pmt" includes extra payments and a Savings column reconciles each row; condensed rows are real Decembers.
- **Rates.** Monthly rates are decimals and are refused above 1 (100% a month) with a message that explains the unit; shares (surplus, auto-invest, minimum payment %) are refused above 1.
- **Money formatting.** `formatCurrency` rounds to cents first (no "−$0.00"); `moneySign` classes anything within half a cent of 0 as zero, not a deficit; `formatCurrencyCompact` picks the unit after rounding (999,960 → "$1M").
- **Opening balances are dated (`balances_as_of`).** A plan's initial savings, initial investments and debt opening balances are ONE set stated as of `finance_plans.balances_as_of` (set on create to the reader's today). Editing any of them — or adding a debt with a non-zero balance — restates the whole set as of today: the edited figure takes the new value and every other one rolls forward to where the calibrated plan stands today (`projectStateAt`), so payments made in between are neither lost nor replayed. An edit is a figure the user CHANGED from what their form showed: the Settings form shows savings and investments where the plan stands TODAY and sends one only when changed (a figure equal to today's position is dropped server-side too); the debt dialog shows the stored opening balance, so a debt's is compared with that. A no-op edit re-dates nothing, and `updatePlan` never writes a balance outside a restatement. Re-dating only the edited figure would treat stale figures as current. Precedence in `calibratePlan`: the latest confirmation wins when it is dated on or after `balances_as_of` (a restatement on the day of a confirmation also updates that confirmation, so a tie is never ambiguous); otherwise the plan's own set is the baseline, as of that day — a day after period 0 rebases the start to its period (end date kept). Null (old rows) falls back to the creation day.
- **Nothing before the start date.** With an anchor day > 1, period 0 begins before the plan's start date (a January plan on day 15 opens Dec 15). The engine never applies flows dated before the start date (the 1st of the start month): inside period 0 the as-of floor is max(as-of, start − 1 day), even when the as-of lies outside period 0 (a plan created before its start). `projectStateAt` reports `before-start` until the start date.
- **Calendar: "Just this month" moves cross months.** A recurring occurrence can be moved to any day of its own month or of the `RESCHEDULE_MARGIN_MONTHS` (2) months either side — in the calendar, any visible cell; further than that the resolver would not find it, so the prompt disables the option and the schema refuses it. Overrides stay keyed by the CADENCE month (the month the cadence put the occurrence in): moving March's rent to Apr 2 writes March's override, April's own rent keeps its own key, and the projection counts no rent in March and two in April. Each chip carries its `cadenceMonth`, so skipping, clearing or re-moving a moved chip acts on its own month's override, not the month it is shown in.
